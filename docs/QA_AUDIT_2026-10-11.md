# QA Audit — search (2026-10-11)

## Verdict
The code is in good health: `cargo test --workspace` is green (778 passed, 0 failed, 3 ignored across 124 test binaries) and the user-visible surface is real — a live `agent0 serve` answered `GET /health` and a real `POST /search` with genuine crawled documents, snippets and per-signal provenance (no mock/placeholder data). The single most serious problem is **documentation drift**: the repo's own authoritative docs (`README.md`, `docs/ROADMAP.md`, `docs/STAGE_STATUS.md`) flatly contradict the shipped code on three named features — the acceptance crate, browser escalation, and the graph lane — and one of them even states the opposite of `crates/embed/Cargo.toml` about the default embedder. Because `README.md` declares `docs/` "the authority" and these docs drive scoping, a reader would under- or over-estimate the system by whole stages. This is a trust defect, not a code defect.

## Findings

### F1 — HIGH — Authoritative docs contradict shipped code on three features
- **What is wrong:** The "Status" section of `README.md:149-150` says the Stage-8 `acceptance` crate is empty, the browser escalation path "is not wired", and the graph lane "is not run". All three are false in the current tree. `docs/ROADMAP.md:49-55` repeats the browser and graph-lane claims (gaps 2 and 3).
- **Evidence (code):**
  - Acceptance crate is populated and green: `crates/acceptance/tests/{fetch_semantics,ingest,portable_round_trip,stage1,stage3,surfaces}.rs`; `cargo test -p search-acceptance` → 13 passed.
  - Browser is wired: `crates/agent0/Cargo.toml:35` (`search-browser` dep), `crates/agent0/src/crawl.rs:442` (`pipeline.set_browser(browser)`), escalation logic at `crates/agent0/src/pipeline.rs:1037-1046`.
  - Graph lane runs: `crates/api/src/graph_lane.rs` exists; `crates/agent0/src/main.rs:116` (`build_graph_lane`), invoked at `main.rs:384`; live log shows `graph lane enabled entities=14659`.
- **What 'fixed' looks like:** Update `README.md` §Status and `ROADMAP.md` gaps 2–3 to match `STAGE_STATUS.md`, or add an "as-of" date and mark those gaps closed with the commit that closed them.

### F2 — MEDIUM — `STAGE_STATUS.md` states the inverse of the code on the default embedder
- **What is wrong:** `docs/STAGE_STATUS.md:72` says "BGE is the default build (`default = ["bge"]`)". The code says the opposite: `crates/embed/Cargo.toml:8-10` — "Off by default: the default build must not need a model download". `docs/ROADMAP.md:57-63` (gap 4) and `benchmarks/results.json:12,20` correctly say the default is the lexical `HashEmbedder`.
- **Evidence:** `crates/embed/Cargo.toml:10` `bge = ["dep:fastembed"]` with no `default = [...]`; `crates/embed/src/lib.rs:45` documents `HashEmbedder` as "the default".
- **What 'fixed' looks like:** Correct `STAGE_STATUS.md:72` to "BGE is opt-in (`--features bge`); default is `HashEmbedder`."

### F3 — MEDIUM — Corpus metrics are stale and undated across docs
- **What is wrong:** `ROADMAP.md:9` says "10 190 indexed documents across 53 hosts"; `STAGE_STATUS.md:23,26` say "11 788+" documents and "69 hosts". The serving index reports **19,255 resources across 222 hosts** (generation 19254; `/var/lib/search/meta.sqlite` `resource` table; `ops/plan.json:79` "live site serves 19,255 pages"), and a separate four-shard fleet build has grown past 323,000 resources / 3,948 hosts. The docs carry no timestamp, so a reader cannot tell which is current.
- **Evidence:** live `/health` generation 19254; `/var/lib/search/meta.sqlite` (`resource`=19255, 222 distinct URL hosts); `ops/plan.json:79`. (CORRECTION to this audit's own first draft: the dense-lane log line reads `docs=12486`, the sidecar's own coverage — **not** 19255; the 19,255 is the index's resource count. The two are different and must not be conflated.)
- **What 'fixed' looks like:** Add an "as-of <date>, generation N" stamp to the corpus figures in `ROADMAP.md`/`STAGE_STATUS.md`, or replace them with a pointer to `ops/state.json`.

### F4 — MEDIUM — The automated "verify" ledger has had false positives
- **What is wrong:** `ops/plan.json:28` records, in the `fast-mode-graph-skip-test` item, that the watcher's own verifier was found broken and had stored the invalid evidence `"error: unexpected argument 'Syntax' found"` from "a cargo command whose failure a pipeline masked." The same item shows the task was re-verified by hand afterward. So the "done" status of ledger items is not, by itself, trustworthy.
- **Evidence:** `ops/plan.json:28`.
- **What 'fixed' looks like:** Fix the watcher's verify path to use `set -o pipefail` / inspect cargo's exit code (the same class of bug is already called out as a retry reason at `plan.json:49,60`), and re-audit the `evidence` fields of items marked `done` before that fix.

### F5 — LOW — Benchmarks are a smoke fixture, not the plan's labelled set (honestly labelled)
- **What is wrong:** Stage 2 asks for 500–2000 labelled queries; `benchmarks/` holds 30 documents / 25 queries (`results.json:7-8,18`).
- **Assessment:** Not a defect in honesty — `results.json:18` says "SMOKE SET, NOT A RESEARCH CLAIM" and `ROADMAP.md:71-74` states it plainly. Recorded so the gap is not mistaken for coverage.

### F6 — LOW — Query-time refresh is silently off while the index is writer-locked
- **What is wrong:** When a crawl holds the index lock, the server serves read-only and query-time refresh is a no-op (observed: `WARN index is locked ... query-time refresh is off`).
- **Assessment:** Honestly logged and documented (`STAGE_STATUS.md:92-94`). Not hidden, but a user expecting `SEARCH_QUERY_REFRESH=1` to refresh during a crawl will get stale results.
